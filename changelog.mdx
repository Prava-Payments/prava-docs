<Update
  label="September 7, 2026"
  tags={["Improvements", "Breaking Changes", "API"]}
  rss={{
    title: "Payment-result card identity and quote context",
    description: "Payment results identify the transaction card. Quote integrations must read merchant_res instead of shop_pay and keep polling while the result is processing."
  }}
>
  <span id="september-2026" />

  ## Payment-result card identity and quote context

  - `GET /v1/sessions/{sessionId}/payment-result` now returns `transactions[].card_id`, the source
    of truth for the card bound to the transaction whether preselected or chosen during collection.
  - Quote-backed results return credential-free transaction summaries and expose merchant checkout
    lifecycle context as `merchant_res`. Non-quote and no-order responses omit the lifecycle field.
  - Results can report `status: "processing"` while payment or merchant checkout is still
    running. For quote-backed sessions, keep polling for the merchant's terminal outcome;
    credential issuance alone does not mean the merchant order is paid.

  **Action required:** Quote integrations that previously read `shop_pay` must now read
  `merchant_res`. Treat `processing` as nonterminal and keep polling.
</Update>

<Update
  label="September 6, 2026"
  tags={["New", "API"]}
  rss={{
    title: "Enroll a card and set up its passkey without a payment",
    description: "Merchant full-enrollment sessions collect or reuse a vaulted card and complete passkey setup without creating an order or transaction. Create the session with your secret key, open its hosted URL, and poll for completion."
  }}
>
  ## Enroll a card and set up its passkey without a payment

  Prepare a customer's card for future payments in a dedicated enrollment flow.
  `POST /v1/sessions/enroll-card` now accepts `enrollment_mode: "full_enrollment"`
  and returns a session that the customer completes on Prava's secure surface.

  Start with an existing `vault_ref_id`, or omit it to let the customer enter a card.
  Full enrollment provisions the card and completes its Visa enrollment and passkey setup
  without creating an order or transaction. The existing `provision_only` mode continues
  to return a `card_id` directly for an already-vaulted card.

  Create the session on your backend using your secret API key:

  ```json
  {
    "enrollment_mode": "full_enrollment",
    "user_id": "customer_123",
    "user_email": "customer@example.com",
    "integration_type": "full_checkout"
  }
  ```

  Open the returned `iframe_url` unchanged. Your backend can poll
  `GET /v1/sessions/{sessionId}/status` to distinguish a provisioned card from completed
  enrollment. Accept success when `status` is `completed` and `outcome` is `fully_enrolled`.
  Retryable failures can be retried inside the same session using the selected card.

  [Set up card enrollment →](/api-reference/enroll-card) ·
  [Poll enrollment status →](/api-reference/get-card-enrollment-status)
</Update>

<Update
  label="August 12, 2026"
  tags={["New", "API"]}
  rss={{
    title: "Create payment sessions from an existing quote",
    description: "Quote-based sessions resolve merchant and product context before creation. The requested amount and currency must match the quote; expired quotes return an error."
  }}
>
  <span id="september-2026-sessions" />

  ## Create payment sessions from an existing quote

  `POST /v1/sessions` supports a quote-based flow: pass the quote ID and Prava resolves
  its merchant, products, and final total before creating the payment session.
  From your backend, authenticate with your merchant secret key and send:

  ```json
  {
    "user_id": "customer_123",
    "user_email": "customer@example.com",
    "total_amount": "49.99",
    "currency": "USD",
    "purchase_context": {
      "quote": true,
      "quote_id": "qte_..."
    }
  }
  ```

  Use the exact final amount and currency of your quote. A mismatch returns
  `409 QUOTE_SESSION_MISMATCH`; an expired quote returns `410 QUOTE_EXPIRED`.
  Omit `custom` in quote mode.

  [Create a session →](/api-reference/create-session)
</Update>

  ## Session purchase context has two explicit modes

  `POST /v1/sessions` now accepts `purchase_context` as an object with two mutually
  exclusive modes: `{ custom: [...] }` for caller-supplied merchant and product details,

<Update
  label="July 19, 2026 — Mandates"
  tags={["New", "API"]}
  rss={{
    title: "Manage standing mandates and reconcile each charge",
    description: "Set up mandates through sessions, filter by customer, inspect charge history, and pause, resume, or cancel future charging. One-time standing mandates are capped at seven days."
  }}
>
  <span id="september-2026-mandates" />

  ## Manage standing mandates and reconcile each charge

  Add `mandate_setup` with `intent: "mandate_setup"` to a session to collect approval
  for future charges. After activation, charge the mandate without another passkey prompt.
  One-time standing mandates are capped at seven days; a later `valid_until` does not extend
  that window. Check `validUntil` before scheduling a charge.

  - **Find the right mandate:** `GET /v1/mandates` accepts `customer_id` for merchant callers,
    using either their external customer ID or a Prava customer ID. Responses include `approvedAmount`, `remaining`,
    `validUntil`, `renewsAt`, and `lastCharge`; the detail endpoint includes charge history.
    Displayed balances are derived from recorded activity; Visa enforces the spending limit.
  - **Track each charge:** `POST /v1/mandates/{id}/charge` creates its own order and transaction.
    Send a decimal-string `amount` and an optional `reference` to deduplicate retries within
    that mandate. Failed charges release the reference for retry. Currency comes from the
    mandate; an optional per-charge `purchase_context` remains a one-entry array.
  - **Report the outcome:** Send `txn_status: "APPROVED"` or `"DECLINED"` to
    `POST /v1/mandates/{id}/charges/{txnId}/report` to reconcile the charge and report to Visa.
    `txn_type` defaults to `"PURCHASE"`.
  - **Control future charging:** `POST /v1/mandates/{id}/pause`, `/resume`, and `/cancel`
    manage the mandate's Prava state. Cancellation is terminal in Prava; these controls
    do not revoke the underlying Visa instruction.

  Charging and reporting require a merchant secret key or a direct agent signature.
  Charge requests are not exposed through MCP.

  [Set up a mandate →](/api-reference/create-session#mandate-setup) ·
  [Charge →](/api-reference/mandate-charge) ·
  [Report →](/api-reference/mandate-report) ·
  [Lifecycle controls →](/api-reference/mandate-lifecycle)
</Update>

<Update
  label="July 11, 2026"
  tags={["Improvements", "API", "CLI"]}
  rss={{
    title: "Replay agent-session requests",
    description: "Agent-session creation accepts an Idempotency-Key and returns the original session on replay. Use a new key for each new purchase and read the approval link from payment_url."
  }}
>
  <span id="september-2026-agent-sessions" />

  ## Replay agent-session requests

  Direct signed-agent integrations can send an `Idempotency-Key` with
  `POST /v1/sessions/agent`. Reusing it for the same agent returns the original session
  with HTTP `200`; a new session returns `201`. A concurrent duplicate can return
  `409 DUPLICATE_EXTERNAL_ORDER_REF`; retry with the same key to retrieve the original.

  This endpoint accepts flat `total_amount`, `currency`, `merchant_name`, `merchant_url`,
  `merchant_country`, and `products` fields. Read the approval link from `payment_url`.
  Use a new idempotency key for each new purchase.

  [Use the current CLI →](/prava-pay/quickstart)
</Update>

  ## Shorter agent approval links and clearer setup recovery

  `@prava-sdk/cli` 2.0.0 updates `prava setup` to register a signed request and print
  a short approval link containing a server-issued link ID. Agent metadata is submitted
  during registration instead of being carried in the approval URL.

  Setup reports expired or denied links and explains when an incorrect system clock
  prevents registration. Polling stops when a link expires and tells you to start setup again.

  ## Choose a default saved card

  `GET /v1/listCards` returns `is_default` and places the default first.
  Merchant secret-key callers can set it with `PATCH /v1/cards/{id}/default` or clear it
  with `PATCH /v1/cards/remove-default`, passing the customer's Prava ID in the
  `customer_id` query parameter.

  [List cards →](/api-reference/list-cards)
</Update>
