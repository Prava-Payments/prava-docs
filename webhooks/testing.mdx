---
title: "Test your integration"
description: "Verify your receiver, test event delivery, and check retries and secret rotation in sandbox."
---

Use sandbox to test your receiver before you activate production delivery. You can use your existing backend or the [optional receiver examples](/webhooks/receiver-examples).

<Tip>A temporary HTTPS tunnel can forward requests to a local receiver. Keep the tunnel running, and update the endpoint if its public URL changes.</Tip>

## What each test proves

| Test | How | Proves |
| --- | --- | --- |
| Verification | **Verify destination** | Your receiver checks the signature and echoes the challenge. |
| Direct test event | **Send test event** in the dashboard | Connectivity and signature handling. Sent straight to your receiver. |
| Queued test event | API test with `queued: true` on an active endpoint | Queued delivery, including automatic retries and replay. |
| Secret rotation | Queued tests during the 24-hour overlap | Both the old and new secrets are accepted. |
| Lifecycle events | Real sandbox payment, card-enrollment or mandate-setup flows | The events your integration actually receives. |

None of the synthetic tests prove that a payment or enrollment happened.

## Verify and send a test event

1. Create a sandbox endpoint in **Webhooks**, select the event types you need, and save its one-time signing secret.
2. Configure your receiver with that secret and the expected application and environment.
3. Click **Verify destination**. Your receiver must validate the signature and return the exact challenge in a small JSON response with a `2xx` status.
4. Select a subscribed event type and click **Send test event**. Confirm your receiver accepts it.

Synthetic events have `test: true`. Accept them to validate delivery, but don't charge, enroll a card or perform other business side effects for them.

## Test automatic retries and replay

The dashboard's **Send test event** goes directly to your receiver. To exercise queued delivery and its automatic retries, activate the verified endpoint and call `POST /v1/webhook-endpoints/{endpointId}/test` with the application's sandbox secret API key:

```json
{
  "type": "payment.credentials_ready",
  "queued": true
}
```

The selected type must be subscribed. See the [Webhook API](/webhooks/api) for authentication and request details.

1. On a controlled test receiver, reject the first synthetic delivery with `503`.
2. Accept its retry with `204`.
3. Check **Delivery history** for both attempts.
4. Open the accepted queued delivery and select **Replay retained event**. The replay should be accepted, but it shouldn't create a second inbox record or repeat business side effects. Its delivery ID changes; its event ID and original body stay the same.

The optional Node example supports the reject-then-accept behavior in sandbox only, with `reject_attempts: 1` in its configuration. Set it back to `0` after testing.

## Test secret rotation

1. Save the current signing secret, rotate once, and save the replacement.
2. During the 24-hour overlap, configure your controlled receiver with **only the old secret** and send a queued test. It should be accepted.
3. Repeat with **only the replacement secret**. It should also be accepted.
4. Leave the receiver configured with the replacement secret.

Use queued tests for this check, because direct test requests use the current secret. Another rotation is blocked until the overlap ends. After the overlap expires, a receiver with only the old secret should reject new deliveries; restore the replacement secret so retries can succeed.

## Test actual lifecycle events

Run the supported sandbox payment, full card-enrollment or mandate-setup flow with the same application. Then compare the persisted API result with the [expected event](/webhooks/events), delivery history and your receiver inbox.

- Check the event's application, environment, resource ID and version.
- Actual lifecycle events aren't marked `test: true`.
- Test completion, failure, cancellation and expiry as separate cases.
- Check that removing a subscription stops new automatic deliveries for that event type.
- Creating a session alone doesn't necessarily produce an event.
- Synthetic financial sandbox simulations don't produce lifecycle events.

## Advanced: automated sandbox receiver

<Accordion title="Optional test-runner controls">
Skip this section for a normal integration. The Node example includes an opt-in control endpoint for a dedicated sandbox receiver driven by an automated test runner.

| Setting | Value |
| --- | --- |
| `WEBHOOK_E2E_CONTROL_KEY` | An independent secret of 32–128 base64url characters |
| `WEBHOOK_E2E_ACCOUNT_ID` | The dedicated sandbox application's ID |

Setting both enables authenticated `/e2e/config` configuration and restricts receipt to that application's synthetic events and signed verification challenges. In this mode the receiver can't validate actual lifecycle events.

- Keep the control key separate from application API keys and webhook signing secrets.
- Keep proxy request bodies and authorization headers out of logs, and use private durable storage.
- The test runner can configure temporary signing secrets, exercise test events and retries, then delete its test endpoint and clear the receiver configuration.
- Leave these options unset on ordinary customer receivers.
</Accordion>
