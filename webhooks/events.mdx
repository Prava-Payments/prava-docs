| Event | Meaning |
| --- | --- |
| `payment.credentials_ready` | Prava issued credentials for this payment attempt. It does **not** mean the merchant charged successfully. |
| `payment.succeeded` | A credentialed payment attempt was confirmed successful. |
| `payment.failed` | An issued payment attempt failed, or Core recorded a definite credential-issuance failure. Inspect `failure_stage` and `error` for the cause. |

V1 covers supported merchant checkout and mandate charge attempts. Agent-account sessions, provision-only synchronous card enrollment, unrelated card lifecycle operations, failures before a durable payment attempt exists, and synthetic financial sandbox simulations are excluded. Full card enrollment and authorize-only mandate setup have separate event families below. Enabling webhooks does not reconstruct past events. Recipients must be verified and subscribed when the event is captured. Active endpoints are eligible for delivery; automatically health-paused endpoints retain selected events without dispatch until resumed, within the original retry window. Manually paused, deleted and unverified endpoints are not selected.

```json
{
  "id": "evt_example",
  "type": "payment.succeeded",
  "schema_version": "2026-10-08",
  "occurred_at": "2026-10-08T10:00:00Z",
  "environment": "sandbox",
  "account_id": "ma_example",
  "resource": { "type": "payment", "id": "txn_example", "version": 2 },
  "data": {
    "session_id": "ses_example",
    "mandate_id": null,
    "order_id": "ord_example",
    "status": "succeeded",
    "amount": { "value": "100.00", "currency": "INR" },
    "outcome_source": "merchant_observed",
    "failure_category": null,
    "failure_stage": null,
    "error": null
  }
}
```

`outcome_source` is `prava_issued` for credentials, `merchant_observed` for quote-backed results reconciled by Core, `merchant_reported` for supported non-quote results, or `prava_observed` for a definite failure Core records before credential issuance. A failed payment keeps the category `PAYMENT_ATTEMPT_FAILED`; `failure_stage` is `payment` for an issued attempt or `credential_issuance` for the supported Core-recorded failures. The error code preserves the known operation result; unknown causes stay generic. Session-user fail reports, unverified legacy reports, transport timeouts and uncertain issuance outcomes never emit `payment.failed`. An API rejection before a transaction exists remains API-only. Payment success/failure does not establish final order settlement. Private provider messages are excluded. [Error reference](/webhooks/errors).

Amounts are decimal strings in the payment's currency. The payment transaction ID identifies the attempt; each new attempt has its own ID. `resource.version` increases for captured changes to that attempt. Persist the highest applied version per resource so an older, late notification cannot overwrite a newer state. Deduplicate by `id` independently of version handling.

Payloads omit payment credentials, network tokens, dynamic CVV, full card numbers, vault references, addresses, email, and raw metadata. Event payloads retain their original schema version and bytes through retries and replays. Additive future fields should be ignored safely.


## Mandate charges and lifecycle

Mandate charges use `payment.credentials_ready`, `payment.succeeded` and `payment.failed`. Newly captured payment payloads include `data.mandate_id` for an owned mandate charge, or `null` for other payment flows. Older retained payloads may omit this additive field. Use the mandate ID to correlate charges without another API request. Issued credentials do not establish payment success or final settlement.

Subscribe separately to the lifecycle events you need:

| Event | Meaning |
| --- | --- |
| `mandate.paused` | An active standing mandate was paused locally. New charges are blocked. |
| `mandate.resumed` | A paused standing mandate was resumed locally. Validity, budget, cadence and charge checks still apply. |
| `mandate.cancelled` | An active or paused standing mandate was cancelled locally. This does not reverse existing payments or confirm card-network revocation. |
| `mandate.expired` | A standing mandate reached its validity deadline, or an eligible mandate was explicitly marked expired. Existing charges are unchanged. |

These events use resource type `mandate` and an `mdt_...` resource ID. They are distinct from setup cancellation and expiry (`mandate.creation_cancelled` and `mandate.creation_expired`). Existing endpoints do not gain the new subscriptions automatically. Agent-owned and internal one-off payment mandates are excluded.

```json
{
  "id": "evt_mandate_example",
  "type": "mandate.paused",
  "schema_version": "2026-10-08",
  "occurred_at": "2026-10-20T10:00:00Z",
  "environment": "sandbox",
  "account_id": "ma_example",
  "resource": { "type": "mandate", "id": "mdt_example", "version": 1 },
  "data": {
    "mandate_id": "mdt_example",
    "order_id": "ord_setup_example",
    "previous_status": "active",
    "status": "paused",
    "valid_until": "2026-10-27T10:00:00Z",
    "recurring_frequency": "one_time",
    "error": null
  }
}
```

The status describes local control, not an available-balance or charge-authorization guarantee. For a resume, `status` is `active`; an already-passed deadline can still prevent charging. `valid_until` can be null for an indefinite recurring mandate or an ambiguous legacy deadline. `recurring_frequency` is `one_time`, `weekly`, `monthly` or `yearly` (or null for a legacy record without a frequency). Lifecycle changes are normal outcomes, so `error` is null. Creation/charge failures retain their respective safe error contracts.

Clock-driven expiry is captured by a background observer in bounded batches. It does not require a status API call and does not mutate financial state. For one-time mandates the deadline is the earlier of the stored deadline and seven days after creation; recurring mandates use their stored deadline, if any. Active and paused mandates can receive clock-expiry notifications; cancelled and consumed mandates do not. Once expiry is recorded, later local pause/resume/cancel changes do not emit another lifecycle notification for that expired mandate. The API can retain its stored `status`; compare `valid_until` with the current time as well as checking `state` and `status`. A paused mandate can still report `state: "paused"` after its deadline. Conflicting stored deadlines are quarantined rather than guessed.

Expiry delivery can be delayed by observer scheduling, a busy source row, or a due backlog. Revalidate the highest resource version and deduplicate event IDs as with other events. Clock-expiry payloads have `previous_status: null`. Deadlines before this family was enabled, including a later re-enablement, are not backfilled. This event family has its own activation boundary. Retained events and replay bytes remain unchanged.

## Enrollment and mandate setup

| Event | Meaning |
| --- | --- |
| `card_enrollment.completed` | Stored card and passkey readiness were persisted. Includes `card_id`, last four digits, normalized brand and expiry, passkey result and consent state. |
| `card_enrollment.failed` | Enrollment failed; `outcome` distinguishes `not_started` from `card_provisioned`. |
| `card_enrollment.cancelled` | The action or session was cancelled. |
| `card_enrollment.expired` | The unfinished session expired. |
| `mandate.created` | One setup attempt is authorized and its mandate is active. Includes `mandate_id` and approved frequency, charge-count terms and an optional decimal cumulative budget. No charge occurred. |
| `mandate.creation_failed` | All setup attempts are currently failed. A later retry can still authorize. |
| `mandate.creation_cancelled` | The unfinished setup session was dismissed. |
| `mandate.creation_expired` | The unfinished setup session expired. |

`mandate.created` preserves the stored approved frequency: current recurring mandates use `weekly`, `monthly` or `yearly`; older records may use uppercase values. New mandate lifecycle events use lowercase values.

These resources are `card_enrollment` or `mandate_setup`, identified by `ses_...`. Consecutive unchanged status writes are deduplicated. A retry that returns to an earlier failure or expiry can publish a new event with a higher version. Each captured status advances `resource.version`; retain the latest version when retries, failures and eventual completion arrive out of order. Completed/failed persisted results take precedence over cancellation/expiry, matching the status API. Expiry is captured by a bounded background scan of unfinished sessions whose expiration occurs after webhook capture starts; enabling webhooks does not backfill past results or expirations.

`card_enrollment.cancelled` preserves its existing `failure_category: null`; the additive `error.code` is `SESSION_CANCELLED`.

Enrollment data contains `session_id`, `status`, `outcome`, `card_id`, `passkey`, `consent_status`, nullable `card` and a fixed `failure_category`, plus a safe `error` for negative outcomes. Mandate data contains `session_id`, `order_id`, `status`, nullable `mandate_id`, nullable `terms` and a fixed `failure_category`, plus a safe `error` for negative outcomes. Raw provider errors, consent references, customer PII, instruction IDs and card tokens are excluded. This does not verify future merchant cancellations or order settlement.

`GET /v1/webhook-event-types` returns descriptions, supported flows, JSON schemas and safe examples for every type. The schema version remains `2026-10-08`; event payload shapes are discriminated by `type`.

`terms.total_budget` is `null` when the stored mandate has no cumulative spend cap; Prava does not substitute a setup or order amount. When present, it is `{ "value": "1200.00", "currency": "INR" }`. `max_charges: 0` identifies a cumulative-budget pool rather than a zero-use mandate. These events describe setup; later charges use the payment event family with a mandate ID. Later pause, resume, cancellation and expiry use the mandate lifecycle events above.


A cancellation or revocation recorded at or after session expiration preserves the
expired result. Earlier cancellation remains cancelled. Persisted completed/failed
results and actual retry transitions keep their precedence and resource versions.
The expiry observer advances through bounded raw batches, so unrelated or ineligible
sessions cannot prevent another application's expiry event.

Repeated revocation retains its original recording timestamp, so retrying a
previous cancellation after expiry cannot change it into an expiry event.

## Quote request failures

Subscribe explicitly to `quote.request_failed` to receive errors from admitted merchant-owned `POST /v1/shop/quote` requests. A quote ID may never have been created, so the resource is a **quote request**, identified by `qreq_...`. The failed HTTP response includes `Prava-Quote-Request-Id` only after an event is confirmed persisted for an active, verified, explicitly subscribed endpoint. Disabled capture, inactive owners, absent eligible subscribers or skipped/uncertain persistence do not receive this header. Each HTTP attempt has its own request/event ID, including attempts that reuse an API idempotency key. Deduplicate event delivery by the event ID.

```json
{
  "id": "evt_example",
  "type": "quote.request_failed",
  "schema_version": "2026-10-08",
  "occurred_at": "2026-10-16T00:00:00Z",
  "environment": "sandbox",
  "account_id": "ma_example",
  "resource": { "type": "quote_request", "id": "qreq_example", "version": 1 },
  "data": {
    "request_id": "qreq_example",
    "status": "failed",
    "failure_category": "QUOTE_REQUEST_FAILED",
    "error": { "code": "VARIANT_UNAVAILABLE", "message": "The selected item is sold out. Choose another variant or product." }
  }
}
```

This event reports the **Core HTTP request's failure**, not the lifecycle of an existing quote or a payment. For example, `QUOTE_TIMEOUT` does not prove that the downstream service created no quote. Reconcile the existing operation and use the API's idempotency rules before retrying. A returned request ID confirms event persistence, not successful webhook delivery or business processing. If capture is skipped or its outcome is uncertain, the original API error is preserved and the header is omitted; an event might still exist after an unconfirmed response. Capture is not automatically retried.

<Warning>
`quote.request_failed` is best-effort before the event is saved. It does not guarantee a notification for every failed quote request. Each Core task captures only one failure at a time; concurrent failures are skipped, and short database timeouts can prevent capture. During bursts such as a downstream outage, many failed requests can therefore have no webhook. These skipped captures are not retried or backfilled. Always handle the API’s error response directly; do not wait for a webhook to learn that the request failed.
</Warning>

Once saved, the event follows the ordinary [delivery and retry rules](/webhooks/delivery). The best-effort limit applies to capture, before those delivery guarantees begin.

Capture uses a dedicated one-connection pool: connection acquisition is limited to 200ms, database lock waits to 75ms, statements to 200ms and client query waits to 250ms. Overlapping capture attempts are skipped immediately. Failures with no eligible subscribers perform no event/counter/version writes.

Authentication, schema validation, rate-limit and invalid-idempotency-key rejections are synchronous admission errors and do not generate this event. Agent-owned requests are outside merchant webhook coverage. Product selection or address confirmation returned successfully is not a quote failure. No request body, address/contact data, product URL, access grant or unverified quote ID is included.

There are currently no independent `quote.ready`, `quote.updated` or `quote.expired` lifecycle events. Expiry reported during a quote request can appear as its error; it is not a background notification that every quote expired. See [coverage and missing events](/webhooks/errors#coverage-boundaries).
