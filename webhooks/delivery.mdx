---
title: "Delivery and recovery"
description: "Handle retries, inspect attempts, and recover missed events."
---

Delivery is **at least once**. Events can be duplicated or arrive out of order. A 2xx response means your receiver accepted the request. Every other status, redirect, DNS/TLS error, or timeout is an unacknowledged attempt. Prava does not follow redirects. HTTP 410 disables the destination; a destination resolving to private or reserved addresses is also disabled.

Automatic delivery allows at most nine network attempts over 72 hours. Known failures while preparing a request, such as a signing-key or database outage, delay delivery and alert Prava without consuming a receiver attempt or opening a receiver-failure incident. An unknown outcome after dispatch begins still counts because the receiver may have accepted it. Retries use increasing delays with jitter; `Retry-After` is bounded to six hours and the remaining retry window. Each request has a three-second connect budget and ten-second total budget. Request bodies are limited to 64 KiB. Prava reads at most 4 KiB of response body; a received 2xx remains accepted even if the body is larger or closes early. Verification requires a complete JSON nonce echo within 4 KiB. Return a small 2xx response after durable acceptance.

Use **Delivery history** to inspect endpoint pause/circuit reasons, open incidents, status, attempt times, HTTP status, safe error category, and the original event body. Ordinary event, delivery and attempt history is retained for 30 days. A fresh replay near that cutoff retains delivery inspection and immutable payload through its 72-hour generation window and any live lease, allowing about 33 days total plus a live lease; it does not receive another 30-day window. New replay eligibility and Events API retention remain 30 days. No raw customer response bodies are shown or logged. Administrators can resolve endpoint problems; developers can replay a retained delivery after verifying and enabling an endpoint subscribed to that event. Replays preserve the event ID/body and create a new delivery generation. Retrying the same delivery and idempotency key returns that original generation even if the endpoint URL has since changed; use a new key for a deliberate replay to a newly verified destination. Expired history cannot be replayed. They cancel pending sibling work, but already transmitted requests cannot be recalled.

To recover events in your own system, call `GET /v1/events?cursor=0` using your application secret key. Process each page durably before saving `next_cursor`. When `next_cursor` is null, that scan is caught up. For later scans, retain the most recent non-null cursor; replaying the last partial page is safe when you deduplicate by event ID. The cursor follows committed capture order within the environment; gaps from other accounts are normal. Recovery does not expose events from another application. Authenticated retained-event and delivery-history reads remain available while Prava delivery is disabled; configuration and replay mutations are paused.

You can retrieve a retained event with `GET /v1/events/{eventId}`. Events may exist even when no endpoint was active; newly created endpoints do not automatically receive past events. Beyond the 30-day window, reconcile your payment records through the relevant API.

Pausing prevents new delivery claims. URL changes clear verification, pause delivery, increment the destination revision, and cancel old queued deliveries. The final recheck cannot recall a request already in transit. Deleting cancels outstanding work and removes the endpoint from the active list.

Five consecutive receiver failures start a five-minute cooldown. A recovery attempt can run after that cooldown. After **eight consecutive receiver-health failures**, the endpoint becomes **Unhealthy · paused** and automatic attempts stop until you explicitly resume it. HTTP 410 and a blocked destination pause it immediately. Receiver-health failures include non-2xx HTTP responses, an explicitly refused connection, supported peer-certificate/protocol errors, and confirmed missing DNS address records. Examples include expired or mismatched certificates and nonexistent domains. DNS confirmation requires negative answers for both IPv4 and IPv6 within the existing DNS budget; an OS lookup failure alone is inconclusive. Resolver failures/timeouts, unreachable networks, connect/response timeouts, connection resets, unknown errors and local trust/configuration failures remain uncertain and do not advance the health streak. Platform preparation failures do not count either. An individual event exhausting its retry limit does not independently pause a healthy receiver. Only one request is in flight per endpoint. Pending deliveries retain the 72-hour and nine-attempt limits; pausing does not extend either window. Shared limits allow at most two concurrent requests and five claims per second per application across workers, with fair account scheduling.

The Dashboard shows safe incident reasons, next-attempt and acceptance times. Exhaustion incidents identify the failed delivery; an unrelated successful request does not clear them. Successfully replaying that event resolves its exhaustion incident, including after a verified destination replacement. The visible operational view refreshes after 30 seconds and backs off to two minutes while unchanged, with jitter; hidden tabs and one-time secret views do not refresh. Incident notices use current authorized developer/admin contacts with verified primary email addresses; retries recheck access and address. We send **one pause email per endpoint outage** to each eligible contact, identifying the endpoint name, application and environment with a link to its settings. Individual exhausted events do not each trigger an email. There are no reminder or recovery emails. An explicit resume/activation closes the previous pause period and resets the health streak. A later pause after eight new consecutive receiver-health failures can send one fresh notice. Editing the URL alone does not start a new notice period. Notices use the transactional email outbox and never go through the failed webhook. Access, verified email and current incident/endpoint state are checked again before sending; outdated queued emails are suppressed. Provider send failures retry the same outbox message with backoff, rather than creating new notices. Queue acknowledgement does not mean an email has been sent.

## Resume an unhealthy endpoint

1. Open **Webhooks** in the developer dashboard and select the environment named in the email. Resellers open **Reseller → Merchants → the application → Webhooks**.
2. Select the named endpoint. Restore the receiver or update its URL, then choose **Verify destination** and the Dashboard’s direct **Send test event**. Direct tests can run while verified delivery is paused.
3. Choose **Resume delivery**. For a replacement URL, the equivalent control is **Activate delivery** after verification. Activation also releases eligible buffered deliveries. To test worker retries, activate first and then send an API test with `queued: true`.
4. Inspect delivery history. Pending deliveries can retry within their original window; replay retained exhausted deliveries as needed. A current-revision queued delivery returning 2xx, including a signed test event, establishes receiver health. It does not prove business processing or automatically resume a manually paused endpoint. Explicit Resume starts a new monitoring period.

For a verified endpoint automatically paused by health or security policy, Prava continues recording new subscribed events as pending deliveries. No request is sent while paused. After explicit resume they can retry within their original nine-attempt/72-hour window; pausing never extends that window. Explicit manual pause opts out of new recipient capture. Replacement URLs require re-verification and cancel old queued work; removed subscriptions, deleted endpoints and periods of globally disabled capture are not backfilled. Use delivery history and the [Events API](/webhooks/api) for retained gaps, and deduplicate by event ID. A stopped development tunnel is a common sandbox cause: restore the tunnel or keep the endpoint paused when it is not in use.


## Endpoint health reasons

The endpoint's `blocked_reason` is nullable:

| Value | Meaning |
| --- | --- |
| `RECEIVER_UNACKNOWLEDGED` | Five consecutive receiver-health failures triggered a five-minute cooldown. |
| `DELIVERY_FAILURE_LIMIT` | Eight consecutive receiver-health failures triggered an automatic pause. Fix and test the receiver, then explicitly resume. |
| `HTTP_GONE` | The receiver returned HTTP 410; delivery is paused. |
| `DESTINATION_BLOCKED` | The destination failed the public-address security check; delivery is paused. |

A null reason does not by itself mean an endpoint is enabled. Check `enabled` and verification state too. Network uncertainty remains visible in delivery history, without being classified as a receiver-health failure.


## Transport failure categories

Delivery history records bounded categories with no raw DNS, certificate or receiver response details:

| Attempt category | Advances endpoint health? | Meaning |
| --- | --- | --- |
| `HTTP_REJECTED`, `REDIRECT_REFUSED` | Yes | A non-2xx HTTP response or redirect. |
| `RECEIVER_CONNECTION_REFUSED` | Yes | The connection was explicitly refused. |
| `RECEIVER_TLS_REJECTED` | Yes | An allowlisted peer certificate or protocol failure, such as expiry, hostname mismatch or a self-signed certificate. |
| `RECEIVER_PROTOCOL_REJECTED` | Yes | An allowlisted malformed HTTP response. |
| `RECEIVER_DNS_NOT_FOUND` | Yes | Both A and AAAA queries confirmed no address records. |
| `DELIVERY_UNACKNOWLEDGED` | No | An ambiguous network/resolver/timeout, local trust/configuration or unknown failure. Normal retry limits still apply. |

These categories guide endpoint health; they do not prove which party caused an outage. A successful 2xx delivery resets the receiver-health failure streak. Ambiguous failures neither advance nor reset it. HTTP 410 and blocked destinations still pause immediately. Requests that already received a 2xx remain accepted even if the connection later closes.
