---
title: "Webhook errors and coverage"
description: "Interpret safe error codes, distinguish request and business outcomes, and understand current coverage."
---

Failure, cancellation and expiry events captured by this release include `data.error` with a stable `code` and a fixed public `message`. Successful/readiness events have `error: null`. Use the code for branching; do not match or parse the message. `failure_category` identifies the broad event family, while the code gives the known cause. Unknown causes stay generic; a generic decline never implies insufficient funds.

Older retained events can omit `error` and `failure_stage`. Retry and replay preserve the original event ID and bytes; they do not add a reason discovered later. Handle absent fields and unknown future codes safely. Later operation outcomes produce new events, with a new resource version where applicable; they do not edit an old event. A new payment attempt can have a different resource ID.

| Negative event | Broad category | Error selection |
| --- | --- | --- |
| `payment.failed` | `PAYMENT_ATTEMPT_FAILED` | Safe persisted attempt code; `failure_stage` distinguishes credential issuance from payment. Unknown cause uses `PAYMENT_FAILED`. |
| `card_enrollment.failed` | `ENROLLMENT_FAILED` | Persisted terminal cause; unknown cause uses `ENROLLMENT_FAILED`. A previous retryable passkey error is not reused as the terminal cause. |
| `mandate.creation_failed` | `MANDATE_SETUP_FAILED` | Most recently created failed attempt when all setup attempts have failed; unknown cause uses `MANDATE_SETUP_FAILED`. A later retry can still succeed. |
| Enrollment / mandate cancellation | `SESSION_CANCELLED` | `SESSION_CANCELLED`; no old retry reason. |
| Enrollment / mandate expiry | `SESSION_EXPIRED` | `SESSION_EXPIRED`; no old retry reason. |
| `quote.request_failed` | `QUOTE_REQUEST_FAILED` | Safe quote HTTP request error; unknown cause uses `QUOTE_REQUEST_FAILED`. Not a quote/payment lifecycle result. |

```json
{
  "failure_category": "PAYMENT_ATTEMPT_FAILED",
  "failure_stage": "payment",
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "The payment was declined due to insufficient funds."
  }
}
```

The following codes are emitted only when that reason was actually persisted or returned at the supported request boundary. Their presence in this reference does not mean every upstream processor can supply them. Raw processor diagnostics and customer data are excluded.

## Coverage boundaries

- **Quote lifecycle:** ready, pricing/shipping updates, automatic expiry and asynchronous quote jobs do not yet have lifecycle webhook events. `quote.request_failed` covers only the admitted Core quote HTTP attempt.
- **Merchant preparation:** a standalone checkout preparation failure or human-verification state that has not become a persisted payment failure has no separate webhook. A timeout or uncertain payment outcome must not be treated as `payment.failed`.
- **More specific merchant causes:** some APIs return a broad checkout code plus a buyer-safe correction message. Webhooks use fixed canonical text for that code and can be less specific. Shipping/stock details are included only when Merchant supplies a supported structured code; Prava does not infer them from text.
- **Before a durable attempt:** authentication, request validation, eligibility/budget checks, unknown resource IDs and errors before a durable payment attempt are returned by the API. They are not financial lifecycle events.
- **Other resources:** standalone provision-only card flows, later card/mandate lifecycle changes, refunds/reversals/disputes, inventory/fulfillment after checkout and agent-account resources do not have these merchant webhook families. No order-fulfillment claim should be inferred from payment success.
- **Delivery errors:** receiver HTTP rejection, signature problems, delivery timeout/exhaustion and internal worker failures belong to delivery history/incidents. They never change `data.error` or create a payment failure.

For payment attempts and full-enrollment results, the safe mapping is shared with the corresponding result projections. The enrollment status API retains its existing `retryable` field for intermediate progress errors; it is not a promise that replaying a webhook retries the operation. Terminal errors use `retryable: false`. Cancellation/expiry now return their own fixed reason instead of an earlier error or an empty reason. Always use `status` to determine the lifecycle.
