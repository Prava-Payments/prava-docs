---
title: "Webhook errors and coverage"
description: "Interpret safe error codes, distinguish request and business outcomes, and understand current coverage."
---

Failure, cancellation and expiry events captured by this release include `data.error` with a stable `code` and a fixed public `message`. Successful/readiness events have `error: null`. Use the code for branching; do not match or parse the message. `failure_category` identifies the broad event family, while the code gives the known cause. Unknown causes stay generic; a generic decline never implies insufficient funds.

Older retained events can omit `error` and `failure_stage`. Retry and replay preserve the original event ID and bytes; they do not add a reason discovered later. Handle absent fields and unknown future codes safely. Later operation outcomes produce new events, with a new resource version where applicable; they do not edit an old event. A new payment attempt can have a different resource ID.

| Negative event | Broad category | Error selection |
| --- | --- | --- |
| `payment.failed` | `PAYMENT_ATTEMPT_FAILED` | Safe persisted issued-attempt code (`failure_stage: payment`), or a definite Core-recorded credential failure (`credential_issuance`, `outcome_source: prava_observed`). Browser reports and uncertain outcomes are excluded. Unknown cause uses `PAYMENT_FAILED`. |
| `card_enrollment.failed` | `ENROLLMENT_FAILED` | Persisted terminal cause; unknown cause uses `ENROLLMENT_FAILED`. A previous retryable passkey error is not reused as the terminal cause. |
| `mandate.creation_failed` | `MANDATE_SETUP_FAILED` | Most recently created failed attempt when all setup attempts have failed; unknown cause uses `MANDATE_SETUP_FAILED`. A later retry can still succeed. |
| `card_enrollment.cancelled` | `null` (unchanged) | `SESSION_CANCELLED`; no old retry reason. |
| `mandate.creation_cancelled` | `SESSION_CANCELLED` | `SESSION_CANCELLED`; no old retry reason. |
| Enrollment / mandate expiry | `SESSION_EXPIRED` | `SESSION_EXPIRED`; no old retry reason. |
| `quote.request_failed` | `QUOTE_REQUEST_FAILED` | Safe quote HTTP request error; unknown cause uses `QUOTE_REQUEST_FAILED`. Not a quote/payment lifecycle result. |

```json
{
  "failure_category": "PAYMENT_ATTEMPT_FAILED",
  "failure_stage": "payment",
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "The payment was declined due to insufficient funds."
  }
}
```

The following codes are emitted only when that reason was actually persisted or returned at the supported request boundary. These tables also cover detailed API errors; code availability alone does not make an outcome eligible for a webhook. In particular, timeout, pending, malformed-response and unknown-issuance codes never produce `payment.failed`. Their presence here does not mean every upstream processor can supply them. Raw processor diagnostics and customer data are excluded.

## Coverage boundaries

- **Quote lifecycle:** ready, pricing/shipping updates, automatic expiry and asynchronous quote jobs do not yet have lifecycle webhook events. `quote.request_failed` covers only the admitted Core quote HTTP attempt.
- **Merchant preparation:** a standalone checkout preparation failure or human-verification state that has not become a persisted payment failure has no separate webhook. A timeout or uncertain payment outcome must not be treated as `payment.failed`.
- **More specific merchant causes:** some APIs return a broad checkout code plus a buyer-safe correction message. Webhooks use fixed canonical text for that code and can be less specific. Shipping/stock details are included only when Merchant supplies a supported structured code; Prava does not infer them from text.
- **Before credentials are issued:** a definite Core-recorded failure can emit `payment.failed` with `failure_stage: credential_issuance` and `outcome_source: prava_observed`. Supported cases include missing token/mandate details, invalid charge context, an unsent charge request and an explicit credential decline. Shopper failure reports, old records without trusted provenance, transport timeouts and unknown issuance outcomes remain excluded. A generic failed status alone is insufficient. A `NO_TOKEN` rejection before a charge transaction exists remains API-only.
- **Before a durable attempt:** authentication, request validation, eligibility/budget checks, unknown resource IDs and errors before a durable payment attempt are returned by the API. They are not financial lifecycle events.
- **Other resources:** standalone provision-only card flows, later card/mandate lifecycle changes, refunds/reversals/disputes, inventory/fulfillment after checkout and agent-account resources do not have these merchant webhook families. No order-fulfillment claim should be inferred from payment success.
- **Delivery errors:** receiver HTTP rejection, signature problems, delivery timeout/exhaustion and internal worker failures belong to delivery history/incidents. They never change `data.error` or create a payment failure.

For payment attempts and full-enrollment results, the safe mapping is shared with the corresponding result projections. Intermediate enrollment errors retain `retryable`; terminal errors use `retryable: false`. A webhook replay retries delivery, not the underlying operation. Always use `status` to determine the lifecycle.

## Result API compatibility

The same recorded failure uses the **same public `error.code`** in the detailed payment-result/enrollment status API and its webhook. Existing codes are preserved, including previously exposed names that mention a card network; this release does not rename, remove or collapse them. You can reuse one error handler. `failure_stage`, `outcome_source` and `failure_category` add context independently of the code.

```json
{
  "failure_stage": "credential_issuance",
  "outcome_source": "prava_observed",
  "failure_category": "PAYMENT_ATTEMPT_FAILED",
  "error": {
    "code": "MANDATE_TOKEN_UNAVAILABLE",
    "message": "The saved card is unavailable for this mandate. Check the mandate's card before trying again."
  }
}
```

Messages come from fixed safe copy; raw provider text is excluded. Unknown codes use the family's generic fallback. Branch on codes, tolerate future codes and absent additive fields, and do not parse messages. Any future public-code rename needs an explicitly versioned API release; there is no calendar cutover or automatic switch.

`PAYMENT_DECLINED`, `USER_CANCELLED`, `AUTH_CANCELLED` and `AUTH_INCOMPLETE` remain distinct. Session-user reports can describe authentication/cancellation or a generic `PAYMENT_FAILED`; a browser-supplied issuer reason is never returned as an attested financial result and never creates `payment.failed` or supplies an issuer reason in any event. Legacy financial claims with caller-controlled diagnostic metadata are also generic. Known non-issuer legacy setup/provisioning aliases stay compatible; stored diagnostics are unchanged.

Cancelled enrollment status responses keep **`error: null`** for compatibility. Use `status: cancelled`; the corresponding cancellation webhook provides `SESSION_CANCELLED` with its unchanged null `failure_category`. Enrollment expiry has the safe `SESSION_EXPIRED` reason. Successful enrollment clears the error. No previous retryable error is reused as a terminal reason.

This shared contract applies to detailed outcome responses and newly captured webhooks. The hosted checkout request uses a separate HTTP error envelope: network failures can return `VISA_PROVISION_FAILED` or `VISA_PROVISION_TIMEOUT`, while the merchant payment-result API contains the specific stored cause. Both existing API contracts are preserved; the webhook matches the detailed payment-result code. Other operation wrappers/admission errors without a recorded outcome remain synchronous API errors. Retained events and replay bytes are never rewritten. Definite credential-issuance events describe failure to obtain credentials, not a merchant charge or final settlement result.


### Confirmed credential-fetch rejections

`FETCH_AGENTIC_CREDS_ERROR` remains the same public code in the detailed API outcome and webhook. A `payment.failed` event with `failure_stage: credential_issuance` and `outcome_source: prava_observed` is sent only when Prava confirms that the credential request was rejected before credentials were issued. This reports failure to obtain credentials; it does not claim an issuer decline or a completed merchant charge.

A timeout, network failure, ambiguous response, or a rejection after the request was already pending does not prove failure and produces no `payment.failed` event. Such outcomes still require checking the status before trying again. Older failures are not backfilled. The internal evidence used to distinguish these cases is not included in the public payload.

Historical codes that include a card-network name remain documented for compatibility because existing integrations already receive them. Their names will change only through an explicitly versioned API release.

### Charge response messages

[Charge a Mandate](/api-reference/mandate-charge) keeps existing known `errorCode` values, including on a deduplicated response. Its `errorMessage` now uses fixed, safe text from this catalog instead of raw provider diagnostics. Match `errorCode` in your handler; do not parse the message for upstream threshold or validation details. Unknown codes use the safe family fallback.
